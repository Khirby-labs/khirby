# docs/journal/devlog/2026-07-24-forms-builder-data-safety.md
Issue:    — · branch worktree-forms-backend-hardening
Goal:     Session 2 of the Forms redesign — stop silent data loss in the builder and bring Forms onto the app-wide conventions (useConfirm + toasts), without the visual redesign (that's S3).
Done:     FormDetailView.vue — unsaved-changes guard (serialized snapshot → isDirty, onBeforeRouteLeave discard-confirm + beforeunload, "Unsaved changes" indicator); toasts on save/copy, errors via inline .crm-error (dropped the "✓ Saved"/"✓ Copied" glyphs); confirm before "Apply template" replaces a non-empty schema; pre-save validation (name, slug pattern, non-empty + unique field names, required-email rule) blocking the round-trip; field reorder (↑/↓, inline SVG) + stable _uid keys instead of :key="idx". FormsView.vue — delete now via useConfirm (removed the hand-rolled AppModal) with toast success/error; toast on create. New specs: FormDetailView.spec.ts (add/remove field, PATCH-on-wire save, save-blocked-without-email), FormsView.spec.ts (create→POST+navigate, delete gated on confirm settle), form-field-templates.spec.ts (slugifyName + every-template-has-required-email invariant). Web suite 46→58 tests / 9→12 files.
Why so:   Kept the existing single-column layout and hand-composed controls untouched — S2 is behavior-only so the S3 visual diff stays meaningful. Client validation deliberately mirrors the S1 server rule (required email) and surfaces it inline, since the backend is now stricter than the old UI. EditableField = FormField & { _uid } with stripUid() on save keeps the wire payload clean while giving v-for stable keys across reorder/remove.
Failed:   design-guard rejected `const confirm = useConfirm()` — its regex /\bconfirm\(/ can't tell the composable from window.confirm. Renamed to `confirmAction` to match the Roles/Users/Pipeline convention (the guard only needs the token not to be literally `confirm(`). Also: kept mocking ../../api/client in the view specs rather than MSW — web.md prefers MSW, but there's no MSW harness yet (that migration is the locked web-p0-msw-specs worktree) and the current green suite (UsersView/RolesView) mocks the client; matched it for consistency.
Next:     Session 3 — the visual redesign (two-column, live preview, tabbed integration, sticky Save via PageActions, field cards, AppTable submissions). Consider promoting the field-type list to one shared source (S5). If MSW lands, re-point these view specs at the network boundary.
