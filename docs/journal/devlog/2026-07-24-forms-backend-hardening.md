# docs/journal/devlog/2026-07-24-forms-backend-hardening.md
Issue:    — · branch worktree-forms-backend-hardening
Goal:     Session 1 of the Forms redesign — close the two production-breaking backend bugs and the server-side validation gaps found in the 5-agent review of main.
Done:     trustProxy on FastifyAdapter (H1); FormsService.assertSchemaCollectsEmail rejects a non-empty schema without a required `email` field on create/update (H2); slug @Matches+@IsNotEmpty, name @IsNotEmpty, field type @IsIn(FORM_FIELD_TYPES) on both DTOs (M1/M2); `select` branch + throw-on-unknown-type in forms-client validate.ts (M2 runtime); `.set(dto as any)` (L2); feedback template email → required. New public-forms.controller.spec.ts (10 cases) + email-required cases in forms.service.spec.ts + select/unsupported-type in forms-client validate.spec.ts.
Why so:   Architecture is email-keyed — contacts.upsertByEmail + the public controller's unconditional assertEmailPresent mean a form with fields but no required `email` can NEVER accept a submission (silently bricked feedback/no-email forms). Chose to reject at write time (honest, single source of truth) over making email conditional, which would need a non-email contact identity the system doesn't have. That decision forced the feedback template (email was optional) to make email required — a form data fix that rides with the backend rule. Reused the FORM_FIELD_TYPES already re-exported by validate-submission-data.ts for the DTO @IsIn rather than adding a 4th copy of the list.
Failed:   Considered the looser rule "schema must merely contain an `email` field (any requiredness)" — rejected: an optional email field still lets a submitter omit email and hit a 400 at assertEmailPresent, so the form is only reliably submittable when email is required.
Next:     Session 2 — builder data-safety & parity (unsaved-changes guard, useConfirm + toasts, confirm-before-apply-template, pre-save schema validation incl. surfacing the required-email rule in the UI, field reorder + stable keys) + FormDetailView/FormsView/store/util specs. The backend rule is currently stricter than the client, so the builder should block Save and explain when a schema lacks a required email field.
